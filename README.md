# Code Review / Зауваження до класу Triangle

1. **Порушення конвенції іменування гетерів:** Методи доступу до полів названі як `takeA()`, `takeB()`, `takeC()`, хоча за стандартами Java прийнято використовувати префікс `get` (`getA()`, `getB()`, `getC()`).
2. **Порушення конвенції іменування сетерів:** Методи зміни полів названі як `putA()`, `putB()`, `putC()`, тоді як стандарт Java вимагає префікс `set` (`setA()`, `setB()`, `setC()`).
3. **Порушення конвенції для булевих методів:** Метод перевірки на рівносторонність названий `equilateral()`, хоча методи, що повертають `boolean`, за стандартами мають починатися з префікса `is` (`isEquilateral()`).
4. **Нестандартні назви методів обчислень:** Метод `perim()` краще перейменувати на загальноприйняте `perimeter()` або `getPerimeter()`, а `area()` на `getArea()`.
5. **Відсутність валідації вхідних даних (від'ємні значення):** Конструктори та сетери не перевіряють, чи є передані сторони додатними числами ($> 0$).
6. **Відсутність перевірки нерівності трикутника:** Відсутній захист від створення невалідного трикутника, де сума двох менших сторін менша або дорівнює третій стороні.
7. **Проблеми з конструктором без параметрів:** Конструктор за замовчуванням `Triangle()` створює об'єкт зі сторонами `0.0`, що суперечить геометричному змісту валідного трикутника.
8. **Дублювання обчислень у формулі Герона:** У методі `area()` півпериметр та вирази з ним обчислюються повторно кілька разів замість збереження в локальну змінну.
9. **Надмірний `if-else` у логічних методах:** Конструкцію з `if-else` у методі `equilateral()` можна спростити, одразу повертаючи результат булевого виразу.
10. **Ігнорування похибки `double` при порівнянні:** Пряме порівняння чисел з плаваючою комою (`==`) у методах типу `equilateral()` або `equals()` є ненадійним через специфіку представлення типу `double` в пам'яті.
